# MSTR Code Model Supremacy Strategy

**Status:** FOUNDER-DIRECTED PROGRAM AMENDMENT / canonical only when merged  
**Date:** 2026-08-27  
**Purpose:** Maximize verified software-building capability per parameter, per GB, and per second while preserving the universal-laptop product boundary.

## Mission

MSTR is not trying to be a small general assistant. It is trying to become the strongest practical tiny/local code-specialized software builder.

```text
PRIMARY_PURPOSE = SOFTWARE_DIRECTION_TO_VERIFIED_WORKING_CODE
PRIMARY_QUALITY = DVCR / DIRECTION_TO_VERIFIED_COMPLETION_RATE
PRIMARY_SPEED = TTVC / TIME_TO_VERIFIED_COMPLETION
PRIMARY_EFFICIENCY = VERIFIED_SOFTWARE_CAPABILITY_PER_GB
```

The scientific target is not an unverifiable claim of absolute superiority over every frontier model. The project target is to maximize coding/building quality inside the non-negotiable product envelope and to make every superiority claim traceable to exact evidence.

## Product Envelope — Unchanged

```text
REFERENCE_TOTAL_RAM = 8_GB
REFERENCE_CONTEXT = 8K
CPU_ONLY_BASIC_OPERATION = REQUIRED

PRIMARY_Q4_ARTIFACT_TARGET <= 3_GB

ACCOUNT_OR_API_KEY_REQUIRED = NO
TELEMETRY_DEFAULT = OFF
WINDOWS + LINUX + MACOS = REQUIRED
FOUNDER_MAC_LARGE_ARTIFACTS = ZERO
```

The research/training system may use cloud GPU compute when separately authorized. Colab/Unsloth are training infrastructure candidates, never end-user product requirements.

## Why This Amendment Exists

The original MSTR-000 candidate scan was designed before the product mission became explicitly code-specialized. T021 filtered out many specialized variants while seeking compact permissive foundations. That heuristic is no longer sufficient: a code-specialized base can now be the preferred foundation if it satisfies rights, trainability, quantization, and universal-laptop evidence.

A concrete example is `JetBrains/Mellum-4b-base`: Apache-2.0, 4B, 8K, code-optimized, trained on more than four trillion tokens and designed for local/developer-tool use. It is not preselected as a winner, but its omission proves that the old search policy is no longer product-aligned.

The amendment also addresses a live governance finding: model-independent MSTR-000A work began before the old `T034_COMPLETE_CANONICAL` entry declaration. Rather than conceal the drift, the program will machine-enforce dependencies and distinguish early-safe infrastructure from candidate-dependent convergence tasks.

## Core Thesis

For a tiny model, the highest-leverage path is not simply more post-training. MSTR must co-optimize:

```text
CODE-SPECIALIZED FOUNDATION
× HIGH-SIGNAL CODE/SOFTWARE DATA
× STUDENT-FRONTIER CURRICULUM
× EXECUTION-FILTERED SELF-ALIGNMENT
× VERIFIED AGENT TRAJECTORIES
× TRAIN/SERVE HARNESS CONSISTENCY
× Q4-IN-THE-LOOP REGRESSION
```

A clever harness cannot permanently compensate for a weak code prior. Agentic RL cannot substitute for insufficient coding knowledge. Conversely, strong code completion without repository/tool/recovery behavior is not the product.

## Pillar 1 — Product-Aligned Backbone Search

Backbone scans MUST include code-specialized base/foundation models rather than excluding them by category.

Every candidate must be evaluated on:

- exact rights and derivative redistribution;
- base vs post-trained provenance;
- architecture and tokenizer;
- code/FIM prior;
- 8K behavior;
- Q4 artifact size;
- CPU runtime support;
- trainability in available frameworks;
- tokenizer code density;
- expected training and inference cost;
- quantization regression;
- raw coding and repository relevance.

`Mellum-4b-base` is a mandatory rescan candidate, not an automatic admission. CodeGemma, StarCoder2, Stable Code and other code-specialized compact families may be reviewed as primary candidates, controls, or reference-only depending on exact rights/product fit.

## Pillar 2 — Tokenizer and Information Density

At an 8K context budget, tokenizer efficiency is product capability.

Measure at minimum:

```text
CODE_BYTES_PER_TOKEN
TOKENS_PER_DIFF
TOKENS_PER_STACKTRACE
TOKENS_PER_TOOL_CALL
TOKENS_PER_FILE_PATH
TOKENS_PER_LANGUAGE_CORPUS
```

A model that fits materially more useful repository context into the same 8K window receives real product value, but tokenizer advantage must not mask model-quality deficits.

## Pillar 3 — Strong Code Prior Before Agent Optimization

MSTR-001 must treat continued code-focused pretraining/mid-training as a first-class hypothesis, not a minor optional step.

Required data families include:

- source code;
- tests and test generation;
- diffs and patch sequences;
- package/build/CI files;
- shell and developer tooling;
- API and schema contracts;
- commits/issues/PRs/reviews;
- repository windows and cross-file dependencies;
- software evolution sequences;
- FIM variants;
- failure/recovery traces.

The data engine optimizes match to the intended software-building distribution, not raw token volume.

## Pillar 4 — Software Evolution Corpus

MSTR must model software as a changing system rather than a static pile of files.

Canonical training/evaluation units should be able to encode:

```text
BASE COMMIT
+ ISSUE / FEATURE DIRECTION
+ INVESTIGATION CONTEXT
+ CHANGE SEQUENCE
+ CI / TEST FEEDBACK
+ REVIEW FEEDBACK
+ REPAIR COMMITS
+ FINAL VERIFIED STATE
```

From this lineage MSTR can derive localization, editing, review-repair, rollback, and stop-decision examples while preserving future-history leakage boundaries.

## Pillar 5 — Execution-Filtered Student Self-Alignment

MSTR should generate part of its own curriculum under a fail-closed verifier pipeline.

```text
student proposes tasks/solutions/tests
-> sandbox executes
-> verifier validates
-> provenance/contamination checks
-> only clean verified examples become positive training candidates
```

Self-generated data is preferred where it matches the student's own distribution. Stronger teacher models may rescue frontier tasks only when output rights are compatible and independent execution/verifier evidence proves the result. Teacher output is never truth merely because the teacher is larger.

## Pillar 6 — Student-Frontier Curriculum

Training data MUST be difficulty-aware.

For each task family estimate student success/difficulty and classify:

```text
TOO_EASY
LEARNABLE_FRONTIER
HARD_FRONTIER
CURRENTLY_UNPRODUCTIVE
INVALID
```

The highest-value training region is the learnable frontier, with deliberate harder-task expansion as capability increases. Difficulty calibration must be refreshed as the model changes.

## Pillar 7 — Test Generation as a Core Skill

MSTR is not only a builder. It must learn to prove that its work is correct.

Train/evaluate distinct but same-model modes:

```text
BUILDER
TESTER
REVIEWER
```

The product default remains one model plus deterministic verifiers, not three separately loaded models. Tool/harness state can select the behavioral mode.

Test-generation curriculum includes:

- reproduce-before-fix;
- targeted regression tests;
- boundary/error-path tests;
- property/metamorphic tests where appropriate;
- tests that fail before the fix and pass after it;
- rejection of tests that merely encode the model's proposed answer.

## Pillar 8 — Verifier Health

`TESTS_PASS` is not automatically ground truth.

Every material training/evaluation task must carry verifier-health evidence. Where appropriate combine:

- build/compile;
- existing tests;
- targeted generated tests;
- type/static checks;
- behavioral/property checks;
- mutation/adversarial tests;
- protected evaluator integrity.

A disagreement or weak verifier moves the example to `EVAL_ONLY`, `REVIEW_REQUIRED`, or `REJECTED` rather than clean positive training admission.

## Pillar 9 — Greenfield + Feature Implementation

MSTR's target distribution cannot be dominated by bug-patch tasks.

Direction-to-Done must contain substantial coverage for:

- feature implementation;
- bounded greenfield programs;
- CLI/API construction;
- cross-file additions;
- integrations and migrations;
- refactors with behavioral preservation;
- build/CI repair;
- test authoring;
- bug repair.

Feature-tree/semantic synthesis is an experimental data-generation arm for progressively increasing complexity from function -> module -> multi-file feature -> small program.

## Pillar 10 — Multi-Fidelity Autoresearch

Full Direction-to-Done evaluation is too expensive for every experiment. MSTR Research Loop must use a promotion ladder:

```text
L0 CONTRACT/SMOKE
-> L1 CODE/FIM/EDIT/TOOL PROXIES
-> L2 EXECUTABLE SMALL-REPO TASKS
-> L3 DIRECTION-TO-DONE / FEATURE / PROGRAM TASKS
-> L4 Q4 UNIVERSAL-LAPTOP REGRESSION
```

Only promising experiments advance. Failed/crashed/invalid experiments remain in the ledger.

The mutable experimental surface may include data mix, FIM ratios, state compaction, context policy, verifier cadence, adapter method/rank, curriculum thresholds, and quantization recipe. Hidden tasks, evaluator authority, product constraints, contamination rules, and rights are frozen per campaign.

## Pillar 11 — Adaptive Agent Loop and Test-Time Compute

`MSTR-BUILD-LOOP-v0` is a state graph, not a ritual linear chain.

A trivial task may take:

```text
GOAL -> ACT -> VERIFY
```

A hard task may loop through localization, planning, execution, testing, and recovery multiple times.

Test-time compute is adaptive:

```text
one attempt by default
-> verifier failure/uncertainty
-> targeted repair
-> optional small bounded branch/best-of-K only when expected DVCR gain justifies cost
```

Measure marginal DVCR gain per extra token, second, and tool action.

## Pillar 12 — Selective Context

The model must learn what context is missing, not merely how to request more.

Canonical context intents include:

```text
NO_RETRIEVAL
NEED_FILE
NEED_SYMBOL
NEED_HISTORY
NEED_TEST
NEED_CONFIG
NO_MORE_CONTEXT
```

The 8K product should prefer compact `AgentState` + recent relevant evidence + minimal repository slices.

## Pillar 13 — Q4 Is the Product

Quantized behavior is evaluated after every material training stage.

```text
checkpoint/master
-> export
-> canonical Q4
-> raw coding/FIM
-> tool/edit/recovery
-> Direction-to-Done
-> 8GB/CPU regression
```

A BF16 improvement that disappears or regresses badly at the release quantization is not accepted as a product improvement.

## Pillar 14 — Training Method Tournament

Framework convenience does not choose the training method.

For compact finalists, a bounded equivalent method tournament SHOULD include, where technically supported:

```text
16-bit LoRA
16-bit LoRA + rsLoRA
4-bit QLoRA
4-bit QLoRA + rsLoRA
```

Full fine-tuning is not default and requires separate evidence/authority. Method selection is based on DVCR, TTVC, direct coding/FIM, Q4 regression, stability, cost, and reproducibility.

Unsloth is a preferred implementation candidate for Colab-accessible experiments, not an architectural lock-in.

## Pillar 15 — Repository Health Over Time

MSTR must not optimize single-task completion while degrading the codebase.

Add `REPOSITORY_HEALTH_DELTA` over multi-round task sequences, including where applicable:

- duplication;
- dead/unused code;
- complexity growth;
- dependency growth;
- architecture violations;
- lint/type debt;
- test health;
- unnecessary refactors.

A model that solves today's ticket by accumulating severe technical debt is not the best software builder.

## Pillar 16 — Cross-Harness Robustness

Training and evaluation must avoid scaffold overfitting.

The same model must retain useful capability across:

```text
RAW_MODEL
H0 NEUTRAL MINIMAL
H1 MSTR NATIVE
H2 WEPLD NATIVE
```

Training may randomize equivalent presentation details where this improves robustness without breaking the frozen semantic contract. Any harness-specific improvement remains separately attributed.
